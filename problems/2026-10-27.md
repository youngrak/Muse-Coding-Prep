## Problem 1: Sensor Calibration Cache

**Topic:** Design — LRU cache (hash map + doubly linked list)

**Google Doc mode:** Solve this problem in a plain text editor with no compiling, and dry-run your code by hand.

**Statement:** A firmware module keeps calibration values for sensors in a fixed-capacity cache. When the cache is full and a new sensor is added, the least recently used sensor entry must be evicted. Both reading and writing a sensor's calibration value count as using that entry. Implement the cache with O(1) average time for both operations.

Implement the class below:

```cpp
class CalibrationCache {
public:
    CalibrationCache(int capacity);
    int get(int sensorId);
    void put(int sensorId, int calibrationValue);
};
```

- `get(sensorId)` returns the stored calibration value for that sensor, or `-1` if the sensor is not in the cache. A successful `get` marks the entry as most recently used.
- `put(sensorId, calibrationValue)` stores or updates the calibration value for that sensor and marks the entry as most recently used. If the cache is at capacity and the sensor is new, evict the least recently used entry first.
- Sensor IDs and calibration values are integers; a stored calibration value is never `-1`.

**Examples:**

```
CalibrationCache cache(2);
cache.put(1, 100);   // cache: {1:100}
cache.put(2, 200);   // cache: {1:100, 2:200}
cache.get(1);        // returns 100, cache order: 2, then 1
cache.put(3, 300);   // evicts sensor 2, cache: {1:100, 3:300}
cache.get(2);        // returns -1 (evicted)
cache.put(1, 150);   // updates sensor 1, cache: {3:300, 1:150}
cache.get(3);        // returns 300
```

**Constraints:**

- `1 <= capacity <= 10000`
- `0 <= sensorId <= 100000`
- At most `100000` calls to `get` and `put` in total.
- `get` and `put` must run in O(1) average time.

## Problem 2: Thread-Safe Sensor Event Queue

**Topic:** Concurrency — mutex, condition variable, producer-consumer queue with shutdown

**Statement:** Several sensor-reader threads produce events and several processing threads consume them through a shared bounded queue. Implement the queue so producers block when it is full, consumers block when it is empty, and a shutdown signal wakes every waiting thread so the system can stop cleanly.

Implement the class below:

```cpp
struct SensorEvent {
    int sensorId;
    long long timestampMs;
    int value;
};

class SensorEventQueue {
public:
    explicit SensorEventQueue(size_t capacity);
    bool push(const SensorEvent& event);
    bool pop(SensorEvent& event);
    void close();
};
```

- `push(event)` adds the event to the queue. If the queue is full, the caller blocks until space becomes available. If the queue has been closed, `push` returns `false` immediately without adding the event. Otherwise it returns `true`.
- `pop(event)` removes the oldest event from the queue and stores it in `event`. If the queue is empty, the caller blocks until an event becomes available. If the queue has been closed and is empty, `pop` returns `false` immediately. Otherwise it returns `true`.
- `close()` marks the queue closed and wakes up all threads waiting in `push` or `pop`. Calling `close()` more than once has no additional effect. After `close()`, events already in the queue can still be popped until the queue is empty.
- The queue must be safe to use from multiple producer and multiple consumer threads at the same time.

**Examples:**

```
SensorEventQueue queue(2);
queue.push({1, 1000, 42});  // returns true
queue.push({2, 1001, 7});   // returns true
// A third push from another thread blocks until a pop frees space.
queue.pop(e);               // returns true, e is {1, 1000, 42}
queue.close();              // wakes all waiting threads
queue.pop(e);               // returns true, e is {2, 1001, 7}
queue.pop(e);               // returns false (closed and empty)
queue.push({3, 1002, 9});   // returns false (closed)
```

**Constraints:**

- `1 <= capacity <= 10000`
- Events are produced and consumed concurrently by an arbitrary number of threads.
- No event may be lost, duplicated, or delivered out of order, and no thread may wait forever after `close()` is called.
