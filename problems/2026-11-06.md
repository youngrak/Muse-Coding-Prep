## Problem 1: Sensor Packet Chain Reversal

**Topic:** Linked lists — reverse nodes in groups of k

**Mode:** Google Doc mode — solve in a plain text editor with no compiling; dry-run by hand.

**Statement:**
A firmware DMA descriptor chain is a singly linked list of sensor packets, each node holding a packet id. Reverse the nodes of the list in groups of `k` at a time: the first `k` nodes are reversed, then the next `k`, and so on. If the number of nodes remaining at the end is less than `k`, leave those nodes in their original order. Return the head of the modified list.

**Function signature:**
```cpp
struct PacketNode {
    int id;
    PacketNode* next;
    PacketNode(int x) : id(x), next(nullptr) {}
};

PacketNode* reversePacketGroups(PacketNode* head, int k);
```

**Example:**
```cpp
// list: 1 -> 2 -> 3 -> 4 -> 5, k = 2
reversePacketGroups(head, 2);  // returns 2 -> 1 -> 4 -> 3 -> 5

// list: 1 -> 2 -> 3 -> 4 -> 5, k = 3
reversePacketGroups(head, 3);  // returns 3 -> 2 -> 1 -> 4 -> 5
```

**Constraints:**
- `1 <= number of nodes <= 5000`
- `0 <= id <= 10^4`
- `1 <= k <= number of nodes`
- Solve iteratively in O(n) time and O(1) extra space (not counting the list itself)

## Problem 2: Firmware Thread Pool

**Topic:** Concurrency / design — fixed-size thread pool with futures and graceful shutdown

**Statement:**
Design a fixed-size thread pool for sensor processing tasks. The constructor takes the number of worker threads. `submit(f, args...)` enqueues a task, runs it on a worker thread, and returns a `std::future` holding the task's return value. `shutdown()` stops accepting new tasks, waits until all queued tasks have finished, and joins all worker threads. If a task throws, the exception must be delivered through its future. Calling `submit` after `shutdown()` must throw `std::runtime_error`. If the pool is destroyed without an explicit `shutdown()` call, it must still shut down cleanly and never deadlock.

**Function signature:**
```cpp
class ThreadPool {
public:
    explicit ThreadPool(size_t numWorkers);
    ~ThreadPool();

    template<typename F, typename... Args>
    auto submit(F&& f, Args&&... args)
        -> std::future<std::invoke_result_t<F, Args...>>;

    void shutdown();

    // No copying; moving is not required.
    ThreadPool(const ThreadPool&) = delete;
    ThreadPool& operator=(const ThreadPool&) = delete;
};
```

**Example:**
```cpp
ThreadPool pool(4);
auto f1 = pool.submit([](int a, int b) { return a + b; }, 2, 3);
auto f2 = pool.submit([] { throw std::runtime_error("sensor fault"); });
f1.get();  // returns 5
try { f2.get(); } catch (const std::runtime_error& e) { /* "sensor fault" */ }
pool.submit([] {});  // OK while running
pool.shutdown();
pool.submit([] {});  // throws std::runtime_error
```

**Constraints:**
- `1 <= numWorkers <= 64`
- Tasks are arbitrary callables with arbitrary arguments and return types
- All public methods must be thread-safe
- Workers must not busy-wait for tasks
- The destructor must never deadlock, even if `shutdown()` was never called
