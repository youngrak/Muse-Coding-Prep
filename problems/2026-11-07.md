## Problem 1: Serialize and Deserialize a Sensor Tree

**Topic:** Trees — serialization / deserialization

**Google Doc mode:** Solve this one in a plain text editor with no compiling — dry-run by hand.

**Statement:** A sensor network is organized as a binary tree: each node is a sensor hub holding an integer reading, with at most one left and one right child hub. Design an algorithm to serialize the tree into a single string, and to deserialize that string back into the original tree. There is no restriction on how the serialization format looks, as long as `deserialize(serialize(root))` reconstructs a tree identical in structure and values to `root`.

```cpp
struct TreeNode {
    int val;
    TreeNode* left;
    TreeNode* right;
    TreeNode(int x) : val(x), left(nullptr), right(nullptr) {}
};

class Codec {
public:
    // Encodes a tree to a single string.
    std::string serialize(TreeNode* root);

    // Decodes your encoded data to a tree.
    TreeNode* deserialize(const std::string& data);
};
```

**Example 1:**

```
Input tree:       1
                 / \
                2   3
                   / \
                  4   5
serialize(root) -> "1,2,#,#,3,4,#,#,5,#,#"   (one valid encoding)
deserialize("1,2,#,#,3,4,#,#,5,#,#") -> the original tree
```

**Example 2:**

```
Input: root = nullptr
serialize(root) -> "#"
deserialize("#") -> nullptr
```

**Example 3:**

```
Input tree:       7
                 /
                7
serialize(root) -> "7,7,#,#,#"   (one valid encoding)
```

**Constraints:**
- The number of nodes in the tree is in the range `[0, 10^4]`.
- `-1000 <= Node.val <= 1000`
- `serialize` and `deserialize` will be called on the same `Codec` object, but the encoding must be self-contained (it may not rely on any state kept between calls other than the string itself).

## Problem 2: Read-Write Lock for a Shared Calibration Table

**Topic:** Concurrency / design — reader-writer lock with writer preference

**Statement:** A firmware calibration table is read concurrently by many sensor threads and updated occasionally by a single calibration thread. `std::shared_mutex` is not available on this platform, so implement your own reader-writer lock using only `std::mutex` and `std::condition_variable` (no busy-waiting / spinning).

The lock must satisfy:
- Multiple readers may hold the lock at the same time.
- A writer holds the lock exclusively: no readers and no other writer while it holds the lock.
- **Writer preference:** once a writer is waiting, no *new* reader may acquire the lock until that writer has acquired and released it (prevents writer starvation).
- No deadlock, and a reader or writer that is waiting must be woken promptly when the lock becomes available to it.

```cpp
class RWLock {
public:
    void lock_shared();    // acquire the read lock
    void unlock_shared();  // release the read lock
    void lock();           // acquire the write lock (exclusive)
    void unlock();         // release the write lock
};
```

**Example:**

```
// Thread R1 holds the read lock.
R1: lock_shared()            // succeeds immediately
// Thread W requests the write lock while R1 still holds the read lock.
W:  lock()                   // blocks
// Thread R2 requests the read lock while W is waiting.
R2: lock_shared()            // must BLOCK (writer preference), even though R1 holds a read lock
// R1 releases the read lock.
R1: unlock_shared()
// W now acquires the write lock; only after W calls unlock() may R2 proceed.
W:  unlock()
R2: lock_shared()            // now succeeds
```

**Constraints:**
- At most `10^4` total lock/unlock calls in a test.
- At most `64` threads may contend for the lock at once.
- `lock_shared` / `lock` may block, but must never busy-wait.
- You may add private member variables and helper methods, but you may not use `std::shared_mutex`, `std::shared_lock`, or any other ready-made reader-writer primitive.
